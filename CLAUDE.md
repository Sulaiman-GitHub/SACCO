## Project

Multi-tenant SaaS for Ugandan SACCOs (savings & credit cooperatives): member, savings, loan and repayment management, plus ML-based loan default risk scoring. `SYSTEM_ARCHITECTURE.md` is the source of truth for scope, module build order (§5), the decisions log (§9) and the UI brand system (§10). Read it before starting a new module. Build modules in order and update that file as modules are completed. Modules 1–8 and 10 (member portal) are done; only the future-work Module 9 remains (documented, not built in the MVP).

## Commands

```sh
composer run setup                 # install, .env, key, migrate, npm build
composer run dev                   # runs `php artisan dev` (server + vite etc.)
composer run test                  # config:clear + full PHPUnit suite
php artisan test --compact tests/Feature/LoanManagementTest.php
php artisan test --compact --filter=testMethodName
vendor/bin/pint --dirty --format agent

php artisan loans:check-overdue                        # flag overdue/defaulted loans; scheduled daily at 01:00 in routes/console.php (needs `schedule:run` every minute via cron, or `schedule:work` locally); output in storage/logs/overdue-scan.log
php artisan audit:verify {sacco_id?}                   # verify audit hash chain + ledger consistency (non-zero exit on problems)
php artisan credit:score-member {member_id} {principal=1000000}
```

ML service (Python, run from the project root so `ml_service.*` imports resolve):

```sh
pip install -r ml_service/requirements.txt   # use a venv at a short path; deep paths exceed Windows limits
python ml_service/run.py              # FastAPI on 127.0.0.1:8001 (GET /health, GET /model-info, POST /score)
python -m ml_service.train            # retrain; writes ml_service/model/model.joblib + metrics.json
python -m ml_service.data.generate_dataset   # regenerate synthetic sacco_credit_data.csv
python -m pytest ml_service/tests
```

Tests use in-memory SQLite (see `phpunit.xml`). Local dev also defaults to SQLite, though the target production DB is MySQL.

## Architecture

**Tenancy.** Every tenant-owned model uses `App\Traits\BelongsToTenant`, which adds the `App\Scopes\TenantScope` global scope and auto-fills `sacco_id` on create from the logged-in user. The scope filters by `auth()->user()->sacco_id`. It is skipped for `super_admin`, returns nothing for a non-super-admin with no SACCO, and **does not apply when nobody is authenticated** (console commands, tests that don't log in). Use `withoutTenantScope()` or `forSacco($id)` for deliberate cross-tenant queries. Any new tenant table needs a `sacco_id` column and the trait. Isolation is covered by `tests/Feature/MultiTenancyIsolationTest.php`.

**Roles & routing.** `users.role` is one of `super_admin`, `sacco_admin`, or `loan_officer`. Middleware aliases are registered in `bootstrap/app.php`: `super_admin` (the `/super-admin/*` platform panel for onboarding SACCOs), `tenant_user` (all tenant workspace routes), and `sacco_admin` (staff management). Controllers are split into `Http/Controllers/SuperAdmin` and `Http/Controllers/Tenant`, and views mirror that in `resources/views/super_admin` and `resources/views/tenant`.

**Append-only ledgers.** `Saving` and `Repayment` throw `RuntimeException` on update or delete unless `Model::$allowLedgerMutations` is set (meant for teardown or maintenance only). Corrections are made with new offsetting entries. Balances are always computed, never stored: savings = `SUM(deposits) − SUM(withdrawals)`, and loan balance = `total_payable − SUM(repayments)`. Loan status (`pending/approved/rejected/disbursed/overdue/defaulted/closed`) is derived in `Loan::refreshStatus()`. A loan is overdue within 90 days past maturity and defaulted after that. Default history is separate from status: `loans.ever_defaulted` and `first_default_date` are set by `Loan::recordDefaultIfDue()` (called first in `refreshStatus()`, so a loan repaid after the threshold is still recorded) and by the model's `saving` hook for any loan saved as `defaulted`. They are never cleared or overwritten, so a defaulted loan that is repaid and `closed` still counts as a past default. The migration `add_default_history_to_loans_table` backfills existing loans, so run `php artisan migrate` on every environment.

**Credit scoring flow.** `TenantLoanController@store` and `@show` call `CreditRiskScoringService::scoreMember()`. That method uses `CreditRiskFeatureExtractor` to build the 8-feature vector from the member's ledger history (feature names must match `FEATURE_NAMES` in `ml_service/train.py`), then POSTs it to the Python service at `config('services.ml_scoring.url')` (`ML_SCORING_URL`, `ML_SCORING_TIMEOUT`). If the service is unreachable or errors, it returns a deterministic heuristic fallback with `success: false` and `model_version: fallback-heuristic-1.0`, so loan operations never fail when the ML service is down. Laravel tests fake the service with `Http::fake`. `risk_score` is the raw, class-weighted model score. It is a ranking score and is what the rule-engine thresholds apply to. `default_probability` is the Platt-calibrated figure (parameters in `metrics.json`), shown only when `probability_calibrated` is true. `feature_contributions` are real per-feature effects in score points against the training-average baselines also saved in `metrics.json`, so after any retrain the service picks up new calibration and baselines automatically. `past_default_count` counts `ever_defaulted` loans, not loans currently `defaulted`; `on_time_repayment_rate` includes ever-defaulted loans whatever their status. `CreditRiskFeatureExtractor` derives a monthly installment schedule from `term_months` to measure on-time repayment, because loans store no schedule. The training data is synthetic (`ml_service/data/generate_dataset.py`). `train.py` compares logistic regression, random forest and gradient boosting, then exports the best model.

**Rule engine.** `LendingDecisionEngine::decide()` turns the assessment into `approve`, `require_guarantor` or `reject` using the SACCO's `LendingPolicy` (`LendingPolicy::resolveFor($saccoId)` creates default thresholds on first use). It runs once, in `TenantLoanController@store`, and saves `decision` and `decision_reason` on the loan. Later policy changes don't rewrite old decisions. `Loan::isApprovalOverride()` makes the approval remarks required when approving against the recommendation. Admins edit the thresholds at `/settings/lending-policy`.

**Reporting.** `PortfolioReportService` feeds the dashboard and the admin-only `/reports` page (CSV exports stream through `TenantReportController`, which prefixes formula-like cells). It groups by month in PHP rather than SQL date functions, so it behaves the same on SQLite and MySQL. `snapshot()` calls `refreshStatus()` on outstanding loans, so overdue and defaulted statuses are up to date whenever the dashboard loads. Charts use Chart.js from a CDN.

**Audit trail.** `AuditTrail::record()` is called from model events (`Saving`, `Repayment`, `Loan`, `LendingPolicy`), so any code path that writes through Eloquent is logged with no controller changes. Loan state transitions are recorded inside `Loan::approve/reject/disburse` within a transaction. `AuditLog` is immutable (updates and deletes throw, with no bypass flag) and each SACCO has its own hash chain over the raw stored values. `details` is stored as a JSON string, not a JSON column, so the hash stays reproducible on MySQL. Bulk query-builder writes and raw DB edits skip the events, and `AuditTrail::verify()` / `php artisan audit:verify` is what catches those. Tests that tamper with data must use `DB::table()`.

**Members.** National IDs are stored only as a SHA-256 hash plus a masked hint (`Member::hashNationalId()`), per Uganda's Data Protection & Privacy Act. Search by NIN works by hashing the search term.

**Consent.** `members` carries `consent_version`, `consented_at`, `consent_captured_by`, `scoring_consent` (null = not recorded, true = agreed, false = declined) and `next_of_kin_informed`. They are not mass assignable: only `Member::recordConsent()` writes them, and each call appends a `member.consent_recorded` audit entry (with the previous scoring choice). Registration requires data-processing consent and an explicit scoring answer; `POST /members/{member}/consent` records or withdraws it later. There is a single strict scoring rule with no mode or environment check: `Member::canBeScored()` is true only when a consent record exists and `scoring_consent` is true. Otherwise (declined, or no record) `TenantLoanController@store`/`@show` and `credit:score-member` skip the ML service entirely and leave `risk_score` and `decision` null for the officer to decide manually. Scoring consent requires data-processing consent: the form disables the scoring answer until data processing is ticked, and `StoreMemberRequest`/`UpdateMemberConsentRequest` reject "scoring yes" without it. Data-processing "no" blocks registration, so "no to both" is never stored. Seed data satisfies the rule the same way real data does: `DatabaseSeeder` creates members through `MemberFactory::consented($staffUser)`, which calls `recordConsent()`. Tests that need scoring must create members with `consented()`. Bump `Member::CONSENT_NOTICE_VERSION` when the notice text in `DATA_PROTECTION_CONSENT.md` changes. Run `php artisan migrate`: existing members get null consent fields.

**Member portal (Module 10).** A read-only, member-facing area at `/portal/*`. Members authenticate on a separate `member` guard (`Member` extends `Authenticatable`, provider `members`); staff use `web`. `auth()->user()` and the default guard stay `web`, so the tenant scope and audit actor logic still refer to staff, and `TenantScope` ignores non-`User` authenticatables. Never call `Auth::shouldUse('member')`; in tests, sign members in with `signInAsMember()` in `MemberPortalTest`, not a bare `actingAs($member, 'member')`. Routes use the `member_portal` middleware (`EnsureMemberPortalAccess`), which signs out members who are inactive, whose SACCO is inactive, or whose portal access was switched off, and holds a member on a temporary password at the password page. Portal controllers start every query from the signed-in member, so there is no route that takes a member ID. Credentials are issued by SACCO admins from the member profile (`Member::issuePortalCredentials()`, `disablePortal()`; username is `m` plus 7 digits, unique across SACCOs). Credential columns are never mass assignable and every issue, reset, disable and member password change is audited without the password. The portal shows no risk score, decision, guarantor or internal notes. A member's consent change is a `ConsentChangeRequest` (opened with `openFor()`, closed by staff with `resolve()`); it never changes `members` consent fields, which only `recordConsent()` writes. `MemberPortalTest` asserts that the only non-GET portal routes are login, logout, password change and the consent request, so a new write route must be added to that allow-list deliberately. Run `php artisan migrate`.

**Frontend.** Blade views use Bootstrap 5 and Bootstrap Icons loaded from CDN in `layouts/app.blade.php`. Tailwind/Vite are present in `package.json` but are not what the current views use. Follow the brand tokens and layout rules in `SYSTEM_ARCHITECTURE.md` §10 for any UI work, including its "Responsive behaviour" rules: every screen must work at about 375px, 768px and desktop. The staff layout (`layouts/app.blade.php`) has an off-canvas sidebar below 992px, list tables use `table-stack` with `data-label` on each cell to become cards on phones, and the member portal (`layouts/portal.blade.php`) is mobile-first with a bottom tab bar. `--color-black` is defined in three CSS blocks (`layouts/app`, `layouts/portal`, `auth/login`) and must be changed in all of them. `tests/Feature/ResponsiveLayoutTest.php` guards the markup the mobile layout depends on. **Never put build or implementation information on a screen a user sees:** no module numbers or build-progress tracking, file names, database field or table names, or internal terms (tenant, rule engine, ML, microservice, append-only, SHA-256, and so on). Use plain words for the audience: "lending policy" not "rule engine", "credit risk score" not "ML score", "savings transaction" not "ledger entry". Keep notes like that in code comments (Blade `{{-- --}}`, never `<!-- -->`, which ships to the browser) or in these docs. `tests/Feature/NoInternalLanguageTest.php` renders every screen for each kind of user and fails if such language appears, so add any new screen to it.
